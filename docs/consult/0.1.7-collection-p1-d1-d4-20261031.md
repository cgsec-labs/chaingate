## P1: our own findings into the pins feed at OSV filing time

(a) **Acceptable, and it is not a new admission path.** pin-admission-1.4 already pins a capture on the operator's category A
approval, independent of OSV. P1 only fixes WHEN that approval is given: at the moment the OSV pull request is opened. The
operator's standing rule stands, an unlabelled hit becomes a pin only when the operator says so on the card; P1 says the filing
is that say-so. A wrong pin BLOCKs installs of one version and is lifted by `allow` or by the ledger at the next cut; the removal
hold applies to a withdrawal as to any removal. The lead-time gain is the whole value: hours instead of the 3 to 5 days an OSV
merge takes.

(b) **Minimum evidence to pin = exactly what the OSV filing requires**, which is why the filing is the right gate: the captured
bytes verified (tarball sha256 and dist.integrity), a stated kind of malware (the report tool refuses without `--kind`), a named
static check firing or a triage-read payload named on the card, not an identity-only beacon (the standing rule), the operator's
approval line. Nothing weaker pins. Names, versions and hashes only in the feed row, never sample content.

(c) **BLOCK, not WARN, and the client shows the source.** A pin is a fact by policy; a weaker "pending" tier would change the
policy identity and teach users that some blocks are negotiable. The row's source is "chaingate-analyst" with an `osv_filing`
status (`filed <date>`, later the MAL id); `why` prints "a ChainGate analyst record names this version; the public advisory is
pending" and the filing date. Nothing in the notice changes.

(d) **No silent expiry.** A pin that protects someone must not lapse because OSV is slow. At 30 days without a merged OSV record
the next cut HOLDS the aged pins to the operator, who re-affirms (another 30 days) or withdraws; the hold path and wording are the
removal hold's. An OSV rejection drops the pin at the next cut, as proposed.

## D1 to D4: order of value, lane, and what is ruled out

The ceiling question first. The metadata ceiling is real and measured (87 percent of first malicious versions fire any metadata
rule; the named set 57 percent on established packages). It is not the project's ceiling: the Stage 0 miss list already names
where the rest is (payload outside the kept files 9, a git dependency 4, no tarball readable 13, hook changed not introduced 4).
So "no, not at a ceiling" is right, and the next recall comes from content and from lead time, not from more metadata rules.

Order of value for 0.1.7, with the lane:

1. **P1** (lead time), 0.1.7: feed and label input, the cheapest recall there is, protecting on the day of the catch.
2. **Keep-list reach** (D4a), 0.1.7: already Stage 5 item 1 for recon, justified by the 9 misses; S2, S3, S6, S7 read one level
   of local requires from main and the hook targets. Measured on the usual sets before naming.
3. **The non-registry dependency rule**, 0.1.7: a release adds a git, URL or file dependency; packument only; 4 misses; a day of
   ops measurement for the base rate. Not in ops' list, but it is the cheapest named rule left from Stage 0.
4. **D3 cooldown**, 0.1.7 as an OPT-IN policy setting, off by default: `on_young_release` WARN or BLOCK under a configurable age
   (72 h). Honest framing: npm 11.10 and pnpm ship this natively, so it is a convenience in the proxy, not detection; its value is
   that ChainGate can exempt what its own signals clear (provenance continuity, a known owner) where the package manager's flag
   cannot. Measure first on the 131: how many first malicious versions were removed within 72 h. That number is the pitch or the
   reason not to bother.
5. **D1 provenance drift**, research lane first: measure provenance coverage in the corpus and, on the 131 takeovers, how many had
   provenance before and what changed (repository, workflow, ref). Rule 4a and provenance-continuity already cover the cheap half;
   cryptographic bundle verification belongs on the server (recon), not in the client, which would otherwise carry a signing
   library for a check the registry already performs at publish. State plainly: the TanStack wave went through the project's own
   trusted-publisher workflow, so D1 catches nothing there; D1 is for the stolen-token and forked-workflow shapes.
6. **D2 tarball versus the source commit**, research lane on the recon card: recon already records 8e (release manifest) and 8f
   (dist literals in the tagged source) as facts. Extend to "files in the tarball absent from the repository at the attested
   commit", measure on the 131 and on art-template and fetch-page-assets, and let the result decide whether a server-side check
   feeds pins through the signed feed. Never in the install path: it needs GitHub.
7. **D4c OpenSSF Package Analysis output**: evaluate access and coverage only. Its findings already reach OSV as MAL records, which
   the seed and feed consume, so the marginal value is the lag between its detection and the MAL record; measure that lag before
   building a reader.
8. **D4d a targeted server-side sandbox**: ruled OUT for 0.1.7. It executes live malware, which every lane's standing rule forbids
   today, so it needs its own isolation design and the operator's ruling on where (a machine with nothing else on it) before any
   paper beyond this line. Research lane, after the archive exists, if the D2 and D4a measurements leave a payload class only
   execution can reach.

Nothing in D1 to D4 is ruled out as an idea; D4d is ruled out for 0.1.7 and until it has an isolation design.
