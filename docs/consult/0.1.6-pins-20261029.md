Asked by the 0.1.6 owner on the operator's word. State received: pins feed part 2 on `claude/chaingate-0.1.6` at e115492
(31c7f19 tests, 96a66dc code), suite 1,695 / 1,654 pass / 0 fail; reads pins-feed-1.3 (ops `ops-pins-feed-1.3` @2a8b2e8, not

## Q1 Default once a URL ships

ON when a URL is configured, as answered on 10-28: `init` prints that the feed is on and which host it reaches; `pins_feed:
false` turns it off; a host without a seed never fetches; README and SECURITY.md state the one outbound connection. Moot until
a URL ships; the operator can flip the default then with one line.

## Q2 Capture pins and `dist.integrity`

Compare and record; the BLOCK stands either way. Your reading is right and the alternative is a bypass: npm versions are
immutable, so when the metadata the proxy holds carries a different integrity than the tarball the analyst verified, either the
metadata is wrong (a mirror, tampering) or the record is wrong, and both are reasons to refuse, not to serve. The seed lane's
"the exact tarball analysed" is evidence binding on the record, not the pin's scope: the pin is (name, version).

- Three recorded outcomes on the row, in plain words: "matches the analysed tarball", "differs from the analysed tarball",
  "no integrity in the metadata".
- A mismatch adds a WARN-level detail beside the BLOCK ("the registry's integrity for this version differs from the analysed
  tarball") and is written to the proxy log once per version, so a wrong record surfaces to ops and is corrected through the
  ledger, never by weakening the decision.
- No policy-table change; `cft-policy-1.3` unchanged.

## Q3 Removal guard

Yes, hold removals too; a stolen key must not be able to silently lift protection. Thresholds as you propose, with two
refinements:

- Hold a cut that removes more than 100 versions, or more than 25 percent of the held rows, whichever is smaller; an empty cut
  over a non-empty held one is always held. Same wording, same `--accept-cut`, same status and doctor path as the addition hold.
- Count removals by (name, version), not by (name, version, advisory_id). A reattribution (a CHAINGATE row replaced by the MAL
  row for the same version, the old id kept in `also_advisories`) is not a removal; counting ids would hold every batch of
  upstream reattributions.
- The hold message names, up to 20, the removed versions this proxy has BLOCKed in the last 30 days (from the witness store), so
  the person deciding `--accept-cut` sees what protection the cut would lift.

## Naming

Rename the user-facing surface to "advisory feed" and keep "pins" internal. `chaingate pin` already means "keep me on this
version", so `update-pins` reads as the opposite of what it does. Lean: command `chaingate update-advisories`, config
`advisory_feed_url` and `advisory_feed: false`, README section "Advisory feed", status line "advisory feed: cut <time>, <n>
versions". The ops artifact keeps its name (pins-feed-1.3, `pins/latest.jsonl`); the witness table may stay `advisory_pins`.
Doing it before any URL ships costs a rename; doing it after costs a deprecation. If the operator keeps `update-pins`, the
README must say in one sentence how it differs from `pin`.

## Exit, unchanged

The fixture-feed tests, a tampered signature refused with the last good kept, an unreachable feed logged once and serving
normally, a row absent from the next cut no longer a pin (now: unless the removal guard holds it), the no-gaps chain, and the
full suite on a non-root host. One notice to the review session and the operator.
