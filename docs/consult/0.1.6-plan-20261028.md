## Q1 Pin overlay: format, signature, key, URL, default

- **Owner of `pins-feed-1.0`:** ops writes the feed; this consult fixes the format; the seed lane does the key ceremony.
- **File:** UTF-8 JSON lines. Line 1 is the header object: `feed_version` ("pins-feed-1.0"), `cut_at` (RFC 3339, UTC),
  `count` (rows that follow), `prev_cut_digest` (sha256 hex of the previous cut's file, or null for the first), `pins_key_id`.
  Each following line is one row: `name`, `version`, `advisory_id` (MAL-/GHSA- id or null), `record_id` (the reviewer category A
  record digest), `source` (one of `osv`, `ghsa`, `chaingate-analyst`), `evidence` ({`kind`: `capture` or `advisory`,
  `sha256`: the captured tarball's sha256, or `advisory_id`}), `added_at`. A cut replaces the previous whole; a row absent from a cut
  is no longer a pin.
- **Signature:** Ed25519 over the file's SHA-256 written as 64 lower-case hex characters as ASCII bytes, no newline, exactly the
  seed's convention (SEEDS.md); `.sig` is the 64 raw signature bytes, as the seed's `.sig`.
- **Key:** no new embedded key. A KEY MANIFEST (`pins/keys.json` + `.sig`), signed by the seed key with the same convention, lists
  delegated keys: `key_id`, `public_key` (PEM), `role` (`pins` or `shards`), `valid_from`, `valid_to` (at most 90 days). The runtime
  verifies the manifest with the embedded seed public key (`witness/seed_verify.js`), then the feed with the manifest key whose
  `key_id` the header names and whose window covers `cut_at`. `key_id` = the first 8 bytes of sha256 over the raw public key, hex
  (the form the seed key id has). Whether any online key exists at all is the operator's open ruling; until it is given and the
  seed lane has run the ceremony, build against a fixture key pair generated in the tests, with the manifest verification path
  exercised by the fixture. There is no published URL or signed sample cut yet; ops' writer exists on this plan but not its first cut.
- **Guards the fetch applies**, each a stated refusal that keeps the last good feed: signature or digest failure; `cut_at` not later
  than the last accepted cut; `prev_cut_digest` not equal to the locally kept previous cut's digest (a fork or replay); `count` not
  equal to the rows; a cut adding more than 2,000 new (name, version) rows over the last accepted cut is HELD and reported
  (`update-pins --accept-cut <digest>` takes it; the largest worm wave was about 1,300 versions). Age: `doctor` warns past 48 h;
  past 7 days the feed is reported stale and the last good keeps serving.
- **Default:** lean ON when the runtime has a configured `pins_feed_url` (one outbound GET pair to that host at proxy start and
  hourly, no identifiers, no registry token); `init` prints that it is on; `"pins_feed": false` turns it off; `--no-seed` and offline
  use never fetch. The alternative, off until `init` asks, is one config line away; the operator rules the default. README and
  SECURITY.md state the new outbound connection either way.

## Q2 Every-download static checks

- **Stage 0 ruling:** not given yet. Ops' step 1 is in (0.1.5 named rows on 85 of 131; 46 misses, 33 with a readable tarball, 1
  armed); step 2 (armed vs unarmed over those tarballs) is running; the operator rules after it, planned Friday 31 Oct.
- **Ceiling:** do not accept "concurrency ceiling" as the norm on every-download, and do not queue (the walk runs on the streamed copy,
  so a queue means buffering). Lean: raise `MAX_ARMED_WALKS` to npm's own default connection count, 16, so in practice no download
  misses its walk; past it keep today's "not walked: ceiling, retried on the next download". Memory is the bound to measure: at most
  6 MiB kept per walk, so about 96 MiB at the ceiling; record RSS in the 500-package test.

  Un-arming changes which rows are computed, not how rows aggregate, so no new identity.

## Q3 Buckets: who, what, when

- **Contract author:** the seed lane. A draft exists on the VPS host (`SEED-CONTRACT-1.3-SHARDS-1.0-DRAFT-20261028.md`, sha256
  2935fb6c...), relayed by the operator; no code until the operator rules on the open items (online key, host, bucket bits).
- **Your reading is right and the plan's "reader unchanged" was wrong.** Corrected design, already agreed with the seed lane:
  - ids become package-scoped under seed contract 1.3: `lineage_id = package_id * 4096 + ord` (checked against v3.2: package ids
    reach 2,320,024, lineages per package reach 2,279), so buckets never collide and importing any set is conflict-free; the full
    `.gz` is built with the same ids so parity holds; 0.1.5 reads 1.2 only, 0.1.6 reads 1.2 and 1.3;
  - the reader gains a new open mode, "cache": one current signed root per cache; a bucket is valid iff the current root lists the
    same logical digest for its bucket id (raw and gz sha256 are transport only); `seed_metadata` comes from the root; the rl1 derived
    table and the read-layout check are per bucket; a stale root (48 h warn, 7 d stale) is stated on every coverage row;
  - checker, placement and policy are unchanged;
  - network on the decision path: `init` pre-fetches the lockfile's buckets so the decision-path fetch is the exception; when it
    happens it runs under the existing evaluation timeout and a failure is the existing "uncovered" outcome, never a clean result;
    `--seed <file>` keeps the full-seed path for CI and offline.
- **In 0.1.6?** Lean: yes as the headline, gated on the three rulings. Order as you state: pin overlay now; item 2 after Friday's
  ruling; buckets only after the contract is accepted and the host and key are ruled. If those rulings slip past mid-November,
  0.1.6 ships without buckets and they become 0.1.7; the operator decides the cut.
