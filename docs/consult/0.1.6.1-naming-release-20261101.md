# Consult: naming and releasing the 0.1.6 fix candidate (review session, 2026-11-01)

Asked by the 0.1.7 owner on the operator's word. Candidate: `claude/chaingate-0.1.6.1` at 4973b67, verified fit (eight signed
commits on 0adee9b, tests before code, four items: the refresh cycle, the not-checked notice, cache-only wording, the report layout).

## 1. The number: 0.1.7

The owner is right: `0.1.6.1` is not semver and npm cannot publish it. A prerelease (`0.1.6-1`) sorts before 0.1.6 and build
metadata (`0.1.6+1`) is ignored by npm. The fix is a patch step, so it is **0.1.7**. In this project every release so far has been a
patch step (0.1.4, 0.1.5, 0.1.6), so there is no spare digit for a hotfix; the honest rule is that patch releases are the only kind
and a release's size is in its notes, not its number. Consequence: the planned collection moves from "0.1.7" to **0.1.8** in the
lane's documents, the README and the consult files from here on.

## 2. Documents

- README: the GitHub Action promise names no version ("a later release"), so the number is never chased again. A "What changed in
  0.1.7" section lists the four items in plain words and states the one deliberate silence: a package absent from the seed stays
  quiet at install (the operator's choice), visible in `report` only. Section headings that say "(0.1.6)" stay; they record when a
  feature arrived. SEEDS.md "0.1.6 or later" stays true.
- npm shows the tarball's README and GitHub shows main's; both update with the release, no separate npm edit, as the owner says.
- The release notes carry the tarball sha256, the signed tag and commit, the record of the reader gates (below), and the sentence
  "changes no decision, policy, check record or seed contract".

## 3. Seed and gates: no seed change, the usual registration

seed-v3.3-full (daaa783e), its tag, assets and the shard host do not change; the client reads the seed by contract version. What
does happen is the standing gate split: at every runtime release the reader gates (M3 to M6, G-PAR, G-REC, the older-client harness,
onboarding) run against the published seed, and the seed owner registers the new tarball's sha in a new release-gates version and
produces the record, as 593630cf did for 0.1.6. The changes are display and a fix, so the gates should pass without a story, but the
rule is not optional and the record is part of the release. 0.1.6 becomes a retained older client in that record, as 0.1.5 is now.

## 4. Process

Same sequence as 0.1.6: signed squash on main, signed tag v0.1.7, `pack` from the tag equal to the tested tarball by sha, the
guarded operator script, the GitHub release. Merge and publish on the operator's go.
